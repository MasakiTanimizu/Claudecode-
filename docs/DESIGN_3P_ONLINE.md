# 三人麻雀オンラインゲーム — 設計メモ (Phase 1-2)

このドキュメントは `開発指示書` セクション64「AIへの実装方針」に基づき、
UI実装前にゲームエンジンの設計を固めるためのメモ。実装は
`src/engine3p/` に配置し、既存の `sanma-tulip-mahjong` UI（`src/App.jsx`）
とは独立したルールエンジンとして開発する（ルールが大きく異なるため）。

## 1. アーキテクチャ方針

- ルールエンジンは純粋関数・イミュータブルなステートオブジェクト中心に実装し、
  UIやネットワーク層から独立させる（section 52 のサーバー権威型設計を見据える）。
- `RuleConfig` を唯一の"マジックナンバー"源とし、牌構成・供託・祝儀倍率などの
  数値をハードコードしない（section 58）。
- 状態は spec section 41 の分類に沿ってオブジェクトを分離する。Phase 1 では
  実際にロジックが必要なものから実装し、未実装のものは将来のフックとして
  型/インターフェースだけ用意する。

## 2. データモデル（Phase 1 実装範囲）

- `TileState`: 牌1枚 = `{ id, suit, rank, variant }`。`variant` は
  `null | 'red' | 'blue' | 'black'`（数牌の5）、`null | 'potchi'`（白のみ）、
  それ以外の字牌・華牌は常に `null`。
- `WallState`: 生山配列 + 王牌（ドラ表示2枚 + 裏ドラ2枚 + 北抜き/華抜き用の
  補充牌プール）。乱数は Web Crypto (`crypto.getRandomValues`) による
  Fisher-Yates シャッフルを使用（section 53: 安全な乱数）。
- `PlayerState`: 手牌・捨て牌・副露・抜き北・抜き華・点数・立直状態。
- `RoundState`: 局・本場・供託・親・ドラ表示牌・裏ドラ・修羅場カウンタ。
- `GameState`: 3プレイヤー分の `PlayerState` + `RoundState` + 完全順位制の
  途中経過。
- `ScoreState` / `ChipState`: 点数と祝儀チップは完全に分離して管理
  （section 12, 40）。
- `RiichiState` / `OpenRiichiState` / `FuroRiichiState`:
  通常リーチ・オープンリーチ・副露リーチをそれぞれ独立フラグとして保持し、
  副露リーチがフリテンになった場合は自動的にオープン化する（section 15）。

Alice / シュバリーチ / 金星・大金星 / 出目金 は Phase 4–5 相当のため、
`ChipEngine` にフック関数（現状は 0 を返すスタブ）として型だけ用意し、
DESIGN 上の接続点を残す。白ポッチは Phase 2 でリーチ後の永続フラグまで
`WhitePotchiState` として構造化したが、"チューリップとして扱う" 和了時の
点数的な意味づけはスペック上まだ確定情報が薄いため、フックのみ残す。

## 3. Phase 1 実装スコープ

`開発指示書` section 62 の Phase 1 に対応:

- 牌生成（112枚、萬子は一萬/九萬のみ）+ 赤青黒バリアント（config駆動）
- 牌山生成・配牌・王牌・ドラ表示2枚
- 3人対戦のターン進行（ツモ・打牌・チー/ポン/カン・ロン）
- 基本役判定（立直・門前自摸・役牌・タンヤオ・平和・一発・海底/河底・
  槍槓・嶺上開花・一盃口・七対子）
- 点数計算エンジン（ツモ損なし、本場加算はスペック通りの固定加算方式）

## 3.5 Phase 2 実装スコープ

`開発指示書` section 62 の Phase 2 に対応:

- `DoraHan.js`: 通常ドラ・赤ドラ（常時+1翻）・裏ドラ（リーチ時のみ）・
  青牌（リーチ時のみ、常に裏ドラ扱いの追加牌として+1翻）・北抜き
  （抜きドラとして+1翻）を合算し、ScoreEngine の翻数に反映。
- `ChipEngine`: 青牌を裏ドラと同じ祝儀バケットに合算するよう更新。
- `SeasonEffects.js` / `FlowerState.js`: 春（抜いた瞬間、保持している
  華牌の枚数だけ即時祝儀を獲得）・夏（和了がワンランクアップ、役満は
  5倍満へ）・秋（手牌中の5がすべて+1翻。黒5はドラ1、赤5/青5は
  ドラ2相当になる）・冬（上下段アリスのフック、Alice実装待ち）。
  ドラ表示牌・裏ドラ表示牌に華牌が出た場合も、和了者に対して同じ
  季節効果が有効になる（`getActiveSeasons`）。
- `WhitePotchiState.js`: 白のうち1枚を `potchi` バリアントとしてタグ付け
  （`RULE_SPECIAL_TILE_MAP` 駆動）。リーチ中に引いた場合は
  `activeBySeat` を永続化、リーチ宣言前に引いた場合は「即白ポッチ」として
  `immediateBySeat` を記録。実際の和了処理（チューリップ化・出目金）は
  スペックの記述だけでは点数計算まで一意に定まらないため未実装。

## 3.6 鳴きルールの変更（house rule）

- **チーを廃止**: `RuleConfig.RULE_CHI_ENABLED = false` を既定値とし、
  `canDeclareChi` は常に `false` を返す。萬子は元々1・9のみで順子が
  作れないため影響なし。設定を戻せば将来バリアントとしてチーを復活
  できる構造は残してある。手牌内で自摸によって順子を構成すること
  自体は引き続き可能（一盃口・平和など順子系の役はそのまま有効）。
- **鳴きの優先度**: `engine/CallPriority.js` を新設。ロンが常に最優先
  （かつマルチロンを許容、頭跳ねルールはスペックに記載がないため
  適用しない）。ポンとカン（大明槓）は同一優先度とし、同時に複数人が
  claim した場合は「打牌者から見た着手順の近さ」でタイブレークする
  （鳴きの種類による優劣はつけない）。

フルの副露バリエーション（暗槓・加槓の詳細タイミング等）、
オンライン対戦、DB、リプレイは引き続き未実装（Phase 3 以降）。

## 3.7 CPU AI 基盤（パラメータ自己更新型）

CPUの学習方式は「パラメータ自己更新型」を採用（TensorFlow等の学習
基盤は使わず、JS内で完結する軽量な強化学習風の重み調整）。

- `ai/Shanten.js`: 標準形・七対子・国士無双のシャンテン数計算。
  標準形はブロック分解の再帰探索（面子・搭子・雀頭候補をメモ化しつつ
  網羅）。`HandParser.isTenpai` との整合性をテストで担保。
- `ai/AIWeights.js`: 評価関数の重みベクトル。spec section 42 の評価
  項目のうち現時点で計算可能なもの（シャンテン数・ドラ・役期待の粗い
  ヒューリスティック・門前維持・安全牌）だけ既定値を持たせ、
  役満期待値・アリス期待値・シュバ期待値・順位期待値・オーラス条件は
  重み0のフックとして温存（該当エンジン実装後に接続する）。
- `ai/HandEvaluator.js`: `Shanten` と `DoraHan` を再利用して手牌の
  評価値を算出。エンジン本体のロジックと評価基準がズレないようにする。
- `ai/DiscardAI.js`: 打牌候補ごとに残り手牌の評価値＋現物安全牌ボーナス
  を計算し、最良の打牌を選択。
- `ai/SelfPlay.js`: 自己対戦による重みの自己更新ループ。候補重み
  （既存重みに乱数摂動を加えたもの）を1〜2席に割り当てて複数局
  自己対戦し、順位ベースの報酬（1位+2・2位0・3位-2）で候補側の平均
  報酬がベースラインを上回った場合のみ採用する（(1+1)進化戦略に近い
  単純な山登り法）。自己対戦のハンドルーチン自体はツモ切り専用の
  簡易版（鳴き・リーチ・北抜き・華抜きは含まない）で、実際の
  `TurnEngine`/`YakuEngine` をそのまま使うため「和了れたら本物の役」
  という一貫性は保たれる。鳴き・リーチ等のAI判断が実装され次第、
  この簡易ループの中身を差し替えるだけで学習ループ自体は変更不要。

CPU AIの実戦投入（各アクションの意思決定を`TurnEngine`のフルフロー
に接続する部分）、統計保存、ランキングは引き続き未実装。

## 4. テスト方針

`vitest` を使用し、`src/engine3p/__tests__/` にモジュール毎の単体テストを
配置する。牌構成・牌山・役判定・点数計算・ドラ計算・季節牌効果・
白ポッチ状態遷移の代表ケースを検証する。
