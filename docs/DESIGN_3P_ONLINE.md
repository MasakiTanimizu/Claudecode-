# 三人麻雀オンラインゲーム — 設計メモ (Phase 1-2)

このドキュメントは `開発指示書` セクション64「AIへの実装方針」に基づき、
UI実装前にゲームエンジンの設計を固めるためのメモ。実装は
`src/engine3p/` に配置し、既存の `sanma-tulip-mahjong` UI（`src/App.jsx`）
とは独立したルールエンジンとして開発する（ルールが大きく異なるため）。

## 1. アーキテクチャ方針

- ルールエンジンは純粋関数・イミュータブルなステートオブジェクト中心に実装し、
  UIやネットワーク層から独立させる（section 52 のサーバー権威型設計を見据える）。
- `RuleConfig` を唯一の"マジックナンバー"源とし、牌構成・供託・祝儀倍率などの
  数値をハードコードしない（section 58）。
- 状態は spec section 41 の分類に沿ってオブジェクトを分離する。Phase 1 では
  実際にロジックが必要なものから実装し、未実装のものは将来のフックとして
  型/インターフェースだけ用意する。

## 2. データモデル（Phase 1 実装範囲）

- `TileState`: 牌1枚 = `{ id, suit, rank, variant }`。`variant` は
  `null | 'red' | 'blue' | 'black'`（数牌の5）、`null | 'potchi'`（白のみ）、
  それ以外の字牌・華牌は常に `null`。
- `WallState`: 生山配列 + 王牌（ドラ表示2枚 + 裏ドラ2枚 + 北抜き/華抜き用の
  補充牌プール）。乱数は Web Crypto (`crypto.getRandomValues`) による
  Fisher-Yates シャッフルを使用（section 53: 安全な乱数）。
- `PlayerState`: 手牌・捨て牌・副露・抜き北・抜き華・立直状態。点数は
  含めない（`ScoreState` に一元化。詳細は 3.10 節）。
- `RoundState`: 局・本場・供託・親・ドラ表示牌・裏ドラ・修羅場カウンタ。
- `GameState`: 3プレイヤー分の `PlayerState` + `RoundState` + 完全順位制の
  途中経過。
- `ScoreState` / `ChipState`: 点数と祝儀チップは完全に分離して管理
  （section 12, 40）。
- `RiichiState` / `OpenRiichiState` / `FuroRiichiState`:
  通常リーチ・オープンリーチ・副露リーチをそれぞれ独立フラグとして保持し、
  副露リーチがフリテンになった場合は自動的にオープン化する（section 15）。

Alice は依然としてフック（`ChipEngine.computeAliceChips` が0を返す
スタブ）のまま。シュバリーチ・金星大金星・出目金・トバしはユーザーへの
確認を経てすべて実装済み（3.10〜3.13節参照）。白ポッチは Phase 2 で
リーチ後の永続フラグまで `WhitePotchiState` として構造化したが、
"チューリップとして扱う" 和了時の点数的な意味づけはユーザーの指示で
一旦保留とした（3.13節）。

## 3.5 Phase 2 実装スコープ

  スペックの記述だけでは点数計算まで一意に定まらないため未実装。

## 3.6 鳴きルールの変更（house rule）

- **チーを廃止**: `RuleConfig.RULE_CHI_ENABLED = false` を既定値とし、
  `canDeclareChi` は常に `false` を返す。萬子は元々1・9のみで順子が
  作れないため影響なし。設定を戻せば将来バリアントとしてチーを復活
  できる構造は残してある。手牌内で自摸によって順子を構成すること
  自体は引き続き可能（一盃口・平和など順子系の役はそのまま有効）。
- **鳴きの優先度**: `engine/CallPriority.js` を新設。ロンが常に最優先
  （かつマルチロンを許容、頭跳ねルールはスペックに記載がないため
  適用しない）。ポンとカン（大明槓）は同一優先度とし、同時に複数人が
  claim した場合は「打牌者から見た着手順の近さ」でタイブレークする
  （鳴きの種類による優劣はつけない）。

オンライン対戦、DB、リプレイは引き続き未実装。

## 3.9 鳴きの実行関数（ポン・カン）

`engine/TurnEngine.js` に実際に副露を成立させる関数を追加した
（`CallPriority.js` は「誰が鳴けるか」の優先度判定のみで、実行自体は
別関数だったギャップを埋める）。

- `declarePon`: 手牌2枚＋直前の捨て牌1枚でポン。捨て牌をその河から
  取り除き、`concealed:false` の面子として追加。手番を鳴いた本人に移す。
- `declareDaiminkan`（大明槓）: 手牌3枚＋直前の捨て牌1枚。王牌から
  補充牌を1枚引く。
- `declareAnkan`（暗槓）: 自分の手番中、手牌4枚のみで成立。
  `concealed:true` を維持するため門前扱いは崩れない。手番は移動しない。
- `declareShouminkan`（加槓）: 既存のポンに4枚目を追加してカン化。
  追加された牌は槍槓（チャンカン）の対象になる。

いずれも成立でイッパツを消し、`round.anyCallMade` を立てる
（天和・地和判定に利用）。チーは house rule により引き続き未実装
（`RULE_CHI_ENABLED=false`）。

**槍槓・嶺上開花の配線**: `checkRonWin` に `{isChankan:true}` オプション
（加槓で追加された牌への振り込みロンを許可）、`checkTsumoWin` に
`{isRinshan:true}` オプション（カンの補充牌でのツモを嶺上開花として
判定）を追加。以前はどちらも`evaluateWin`内でハードコードでfalseに
なっており、実際には発生しえなかった。

暗槓・加槓に対する他家の“槍槓”優先権や、カンの成立自体に対する
`CallPriority`との統合（大明槓は他のポン/ロンとの優先度勝負が必要）は
まだドライバー層（呼び出し側）の責務として残しており、本エンジンは
プリミティブを提供するのみ。

## 3.8 特殊役・役満（Phase 3）

- `yaku/YakuEngine.js` に section 19-21/27 の通常役を追加:
  一気通貫・混全帯么九/純全帯么九（チャンタ系2倍ルール適用）・
  対々和・三暗刻（ロンで刻子を完成させた場合は明刻扱いにする通常の
  符計算と同じ規約を適用）・三色同刻（萬子が1・9のみのため111/999
  のみ成立）・三槓子・小三元（役牌分と加算）・三連刻・三風（北は
  常に手牌として使えないため東南西固定）・二盃口（一盃口とは排他）・
  混一色/清一色。
- `yaku/Yakuman.js`（新設）: 役満判定を独立モジュール化。国士無双・
  四暗刻（ロンでの槍槓待ちでない刻子完成は不成立）・大三元・字一色・
  小四喜・大四喜・清老頭・緑一色・四槓子・天和・地和、および
  section22の特殊役のうち役満扱いのもの（四連刻・萬子の混一色・
  清一色七対子）を実装。複数の役満形が同時に成立しても、スペックが
  役満の重複加算（ダブル役満）に触れていないため加算せず、
  常に固定翻数(13翻相当、ScoreEngineのmangan+テーブルでbase=8000)
  として扱う。
- **北の使用制限を修正**: これまで手牌に北(z4)が混ざっていても
  通常役として和了できてしまう抜け穴があった。`TurnEngine.evaluateWin`
  に北使用ガードを追加し、国士無双・字一色・小四喜・大四喜以外の
  形では北を含む「完成形」を和了不可（`invalid_north_usage`）とする。
- **天和・地和**: `RoundState` に `totalDraws` / `firstDrawDoneBySeat` /
  `anyCallMade` を追加し、「その席にとって最初のツモ」かつ「まだ誰も
  鳴いていない」状態を判定する。鳴きの実行関数（ポン/カン成立処理）は
  まだ未実装のため `anyCallMade` は現状常にfalseだが、実装され次第
  自動的に正しく効くようにフィールドだけ先に用意してある。
- `chips/ChipEngine.js`: 純正役満/数え役満の祝儀（section32、夏で
  昇格）を配線。

## 3.7 CPU AI 基盤（パラメータ自己更新型）

CPUの学習方式は「パラメータ自己更新型」を採用（TensorFlow等の学習
基盤は使わず、JS内で完結する軽量な強化学習風の重み調整）。

- `ai/Shanten.js`: 標準形・七対子・国士無双のシャンテン数計算。
  標準形はブロック分解の再帰探索（面子・搭子・雀頭候補をメモ化しつつ
  網羅）。`HandParser.isTenpai` との整合性をテストで担保。
- `ai/AIWeights.js`: 評価関数の重みベクトル。spec section 42 の評価
  項目のうち現時点で計算可能なもの（シャンテン数・ドラ・役期待の粗い
  ヒューリスティック・門前維持・安全牌）だけ既定値を持たせ、
  役満期待値・アリス期待値・シュバ期待値・順位期待値・オーラス条件は
  重み0のフックとして温存（該当エンジン実装後に接続する）。
- `ai/HandEvaluator.js`: `Shanten` と `DoraHan` を再利用して手牌の
  評価値を算出。エンジン本体のロジックと評価基準がズレないようにする。
- `ai/DiscardAI.js`: 打牌候補ごとに残り手牌の評価値＋現物安全牌ボーナス
  を計算し、最良の打牌を選択。
- `ai/SelfPlay.js`: 自己対戦による重みの自己更新ループ。候補重み
  （既存重みに乱数摂動を加えたもの）を1〜2席に割り当てて複数局
  自己対戦し、順位ベースの報酬（1位+2・2位0・3位-2）で候補側の平均
  報酬がベースラインを上回った場合のみ採用する（(1+1)進化戦略に近い
  単純な山登り法）。自己対戦のハンドルーチン自体はツモ切り専用の
  簡易版（鳴き・リーチ・北抜き・華抜きは含まない）で、実際の
  `TurnEngine`/`YakuEngine` をそのまま使うため「和了れたら本物の役」
  という一貫性は保たれる。鳴き・リーチ等のAI判断が実装され次第、
  この簡易ループの中身を差し替えるだけで学習ループ自体は変更不要。

CPU AIの実戦投入（各アクションの意思決定を`TurnEngine`のフルフロー
に接続する部分）、統計保存、ランキングは引き続き未実装。

## 3.10 シュバリーチ・シュバゾーマ・シュバンテ（ユーザー回答による確定仕様）

開発指示書 section 14/36 は「通常リーチ供託1000点」と「シュバリーチ等の
35000点」が矛盾していたため、ユーザーに確認し以下で確定：

- 通常リーチ: 供託1000点
- シュバ / シュバゾーマ: 供託1000点（通常リーチと同額）＋シバ棒消費
- シュバンテ: **持ち点全て**を供託（要: 供託前の持ち点 > 60000）＋シバ棒消費
- シバ棒は「点棒」ではなく**1局につき1回だけ使える許可トークン**として
  実装した（`state/ShubaState.js`）。各局開始時に全員1本ずつ持ち、
  シュバ/シュバゾーマ/シュバンテいずれかを宣言すると消費される
  （`RULE_SHUBA_STICK_VALUE=100` は卓上表示用の値であり、点数計算には
  一切使わない — 持ち点全てを供託するシュバンテの後に別途100点を
  差し引こうとすると破綻するため）。
- 和了時祝儀倍率: シュバ×2・シュバゾーマ×3・シュバンテ×10。
  ユーザーの指示により、この倍率は**和了り祝儀・華牌祝儀（春の即時
  祝儀）・トビ祝儀のすべてに適用される**。華牌祝儀は抜いた瞬間に
  等倍で即時支給済みのため、`PlayerState.hanaChipsThisHand` に
  当局分を記録しておき、シュバ勝ちが確定した和了時に
  「倍率適用後の総額 − 既払い分」だけを追加精算する
  （`ChipEngine.computeChips` の `hanaChips`/`alreadyPaid`）。
  トビ祝儀自体はまだ未実装（成立条件が別途未確認）だが、実装時は
  同じ `computeShubaMultiplier` の対象にする。
- `TurnEngine.declareRiichi` に `shubaTier` オプションを追加し、
  供託計算・シバ棒消費・コスト検証（シュバンテの60000点条件、
  シバ棒の二重使用禁止）をまとめて行う。

**副産物のバグ修正**: この実装中に、`PlayerState.score` と
`ScoreState`（`GameState.score` 配列）が同じ点数を別々に保持し、
互いに同期しないという実装上の不整合を発見した。和了・本場・
ノーテン罰符の決済はすべて `game.score` 配列に対して行われる一方、
`declareRiichi` は誤って `player.score` を増減しており、実際には
リーチ棒の供託がスコアへ反映されないバグになっていた。
`PlayerState` から `score` フィールドを削除し、点数は
`ScoreState`（`game.score`）に一元化した（spec section 12/41 の
「Score/Chip/RankPoint/Bonus を別々に管理する」という設計方針にも
合致する）。

## 3.11 金星・大金星（SpecialBonusRule）と祝儀のゼロサム化（ユーザー回答による確定仕様）

- 成立条件: 捨て牌の**8巡目**にツモ／ロン和了で金星、**16巡目**で大金星。
  ポン・カンでターン順が飛んでも「じゅんめ」自体はそのまま適用される
  （ユーザー指示）。

- **じゅんめの定義（一度誤った実装をユーザーに訂正いただいた）**:
  最初は `RoundState.totalDraws`（生牌山からの通常ツモ回数）から算出
  していたが、これは誤り。ポンで鳴いた本人は牌山からツモらずに
  そのまま打牌するため、ツモ回数ベースだと鳴きが起きた分だけ
  じゅんめが正しく進まなくなる。ユーザーの指摘（「要は捨てる牌の場所
  なので、8巡目でポンで流された場合はその次が8巡目の位置と計算する」）
  を受け、**`RoundState.totalDiscards`（打牌の総数。鳴き直後の打牌も
  含めすべての打牌をカウント）**から `ceil(totalDiscards / 3)` で
  導出するよう修正した。鳴きで本来の巡目位置の牌が消費されても、
  「次の打牌」が同じ巡目位置としてカウントされる。
  じゅんめ自体は独立フィールドとして保持せず、`totalDiscards` から
  都度計算する（点数と同じ二重管理バグを繰り返さないため）。

- **祝儀のゼロサム化**: 当初、金星・大金星だけを「放銃者から3枚獲得」の
  ようなゼロサム授受として実装し、他の祝儀カテゴリ（赤牌・一発・
  裏ドラ・北抜き・役満・華牌祝儀）は「勝者への一方的な付与」のまま
  だったが、ユーザーに確認したところ**全カテゴリを金星・大金星と
  同じゼロサム方式にする**との回答を得た。

  - `chips/ChipPayment.js`（新設）: `distributeZeroSumChips(perPayer, {...})`
    を共通ロジックとして切り出し、`SpecialBonusRule.js` と
    `TurnEngine.resolveWin` の両方から利用する。
  - `ChipEngine.computeChips` が返す `total` は「勝者への一方的な
    給付額」ではなく「放銃者換算の1人あたり支払額（ロン時の基準額）」
    として再定義した。実際の座席別の授受（ツモ: 対戦相手それぞれが
    `total` を全額支払い、勝者は人数分を受け取る／ロン: 放銃者のみが
    `total` を支払う）は `TurnEngine.resolveWin` 側で
    `distributeZeroSumChips` を通して行う。`ChipEngine.js` 自体は
    座席情報を持たないため、この責務分担にした。
  - シュバ倍率は金星・大金星を含むすべての祝儀カテゴリに適用する
    （和了り祝儀の一種のため）。授受の両側（勝者の受け取り・支払者の
    失う分）を同じ倍率でスケールする。

## 3.12 出目金（DemekinRule、ユーザー回答による確定仕様）

- 成立条件（section35: 純正役満・4花・4北・即白ポッチ）: いずれか成立時、
  和了時のみ発動（条件成立の瞬間ではない）。複数条件が同時成立しても
  サイコロは1回のみ振る（役満の重複と同様、加算の規定が仕様書にない
  ための仮決め）。
- サイコロシステム: `chips/DiceEngine.js` の `rollDice()`。`Wall.js` の
  シャッフルと同様、Web Crypto による安全な乱数を使用（section53と
  同じ設計思想をサーバー権威型の乱数にも適用）。
- 支払い: 出た目の数だけ、他の祝儀カテゴリと同じゼロサム方式で決済
  （ロン: 放銃者のみが支払う／ツモ: 対戦相手それぞれが出た目の数だけ
  支払う。ユーザー例:「サイコロ2が出れば2枚ずつ支払う」）。
  `chips/DemekinRule.js` が `chips/ChipPayment.js` の
  `distributeZeroSumChips` を再利用して実装。既存の祝儀カテゴリ
  （赤牌・役満など）とは別枠で加算され、同じ和了に対して両方が発生する
  （例: 純正役満10枚 ＋ 出目金（サイコロの目）枚）。
- シュバ倍率は出目金にも適用する（和了り祝儀の一種と解釈、金星・大金星
  と同様の仮決め）。
- 「4花」「4北」は和了ったプレイヤー自身がそのハンドで4枚すべてを
  抜いている場合のみ成立（`player.flowerTiles.length >= RULE_FLOWER_COUNT`
  / `player.kitaTiles.length >= RULE_NORTH_COUNT`）。「即白ポッチ」は
  `WhitePotchiState.immediateBySeat`（リーチ宣言前に白ポッチを引いた
  状態）を流用。

## 3.13 トバし・白ポッチ・流し役満（ユーザー回答による確定/保留）

- **トバし（確定）**: 0点も飛び扱い（マイナスだけでなく0点ちょうども
  含む）。飛ばされたプレイヤーが、飛ばした（＝その支払いの原因となった
  和了の）プレイヤーに祝儀10枚を支払う。1つの和了で2人同時に飛んだ
  場合はそれぞれが10枚ずつ支払う（ユーザー例:「2人のプレイヤーが1人の
  プレイヤーに飛ばされた場合、10枚ずつ飛ばしたプレイヤーに支払う」）。
  実装は `chips/TobashiRule.js`。判定は「その和了の点数決済（本場・
  供託回収を含む）を適用した結果、0点超→0点以下に転落したか」という
  **遷移**で行う。単に「現在0点以下か」で判定すると、既に飛んでいる
  プレイヤーが後続の局でさらに失点するたびに再課金されてしまうため。
  流局時のノーテン罰符やリーチ供託などトバしの原因が単一の「和了者」に
  帰着しない決済は対象外（和了時の決済のみを対象とする、という仮決め）。
  シュバ倍率も適用する（ユーザーが最初のシュバ確認時に「トビ」を
  明示的に倍率対象として挙げていたため）。
- **白ポッチ（保留）**: "チューリップとして扱う" 和了の点数的意味づけは
  一旦解除（ユーザー指示）。`WhitePotchiState` の構造（reveal/active/
  immediate の追跡）自体は維持し、`immediateBySeat`（即白ポッチ）は
  出目金のトリガー条件として引き続き使用する。`activeBySeat`
  （リーチ後永続化）は現状どのスコアリングからも参照されない。
- **流し役満（確定）**: 本ルールでも通常の流し満貫と同じ「自分の捨て牌が
  全て么九牌（1・9・字牌）で、誰にも鳴かれず、流局する」という条件で
  確定。ただし実装には「そのプレイヤーの捨て牌が一度も鳴かれていない
  か」の履歴と「流局まで到達したか」の判定が必要で、現状の
  `resolveExhaustiveDraw` はテンパイ判定のみを行っており、この履歴を
  追跡していない。役自体の実装は今後の課題として残す。

## 3.14 役満点数表・リーのみ・カンドラ（ユーザー回答による確定/訂正）

- **役満の点数（訂正）**: 当初、役満は一律base=8000として通常の
  fu×2^(2+han)由来の重み付き丸め計算（`computeWinPayments` の既存の
  ツモ按分ロジック）に流し込んでいたが、ユーザーが実際の三人麻雀の
  役満点数表で訂正:
  子ロン32000／子ツモ12000(他家)+20000(親)／親ロン48000／
  親ツモ24000オール。
  これは満貫(base=2000)を基準ユニットとした単純な線形スケール
  （`multiplier = base / 2000`）で正確に説明できる数値だったため、
  `ScoreEngine.computeManganPlusPayments` という固定支払いテーブルを
  新設し、`computeWinPayments` は `base >= 2000` の場合すべてこちらに
  委譲するようにした。満貫・跳満・倍満・三倍満はユーザーから直接
  確認を得たわけではないが、役満の数値がこの線形スケールに正確に
  一致する以上、他の解釈と矛盾しない自然な拡張として同じテーブルを
  適用している（実際の麻雀でも満貫以上は連続計算式ではなく暗記された
  固定点数表を使うのが通例）。
- **リーのみ（新規実装）**: 立直だけが役で他に一切役がない和了は、
  実際のhan/fuに関わらず固定で**5倍満**（`RULE_RIICHI_ONLY_BASE=10000`,
  上記固定表のmultiplier=5）となる。ドラは「役」ではないため判定に
  影響しない（`yakuResult.yakuList` の中身だけを見る）。
  「オープンのみ」という独立した役は存在せず、オープンリーチ宣言
  そのものの定義であることが確認できたため、別実装は不要。
- **カンドラ（訂正）**: 当初「本ルールはカンドラを実装しない、ドラは
  常時固定2枚」という前提で進めていたが、ユーザーが実装する方針に
  訂正。カン（暗槓・大明槓・加槓）のたびにドラ表示牌を1枚追加公開し、
  対応する裏ドラ候補（カン裏ドラ）も1枚ずつ非公開で追加する。
  - `wall/Wall.js`: 王牌のレイアウトに `kanDoraPool` /
    `kanUraDoraPool`（既定 `RULE_MAX_KAN_DORA=4` 枚ずつ）を新設。
    `revealKanDora` / `revealKanUraDora` で1枚ずつ消費する。
  - `engine/TurnEngine.js`: `declareDaiminkan` / `declareAnkan` /
    `declareShouminkan` すべてで `revealKanDoraForGame` を呼び、
    `round.doraIndicators` / `round.uraDoraIndicators` に追加する。
  - **アリスの開始位置**: ユーザーの回答「次に槓する予定だった牌から
    アリス開始」を反映し、`Wall.peekNextAliceTile` を新設（王牌内で
    次に消費されるはずの `kanDoraPool` の先頭、それも尽きていれば
    `replacementPool` の先頭を指す）。アリスエンジン本体（めくり・
    ヒット判定・連鎖処理）はまだ実装しておらず、王牌レイアウトを
    正しい形にして接続点を用意しただけの段階。
