# STEP2: システム構成図

## 全体像

- **Flutterクライアント**は`mahjong_engine`を内蔵し、CPU戦（オフライン）はサーバー通信なしでクライアント内のみで完結する
- **オンライン対戦**時はクライアントとサーバーがWebSocketで通信し、サーバー側も同じ`mahjong_engine`を内蔵して権威判定を行う（①着手・操作をRPCで送信 → ②盤面更新・イベントをStreamで配信）
- クライアント側の`mahjong_engine`とサーバー側の`mahjong_engine`は**同一のDartパッケージ**であり、ロジックを完全共有する（二重実装なし）

## サーバー内部構成

- **Authモジュール**: Google / Apple / ゲストログイン。OAuthトークン検証を行う
- **マッチング/ルーム管理**: 乱数マッチ・友人戦・再接続を担当。Redisにキュー登録・ルーム状態・再接続トークンを読み書き
- **mahjong_engine（サーバー = 権威判定）**: クライアントの操作を再検証

## データストア

- **PostgreSQL**: アカウント / レート / 段位 / 対局履歴 / リプレイ
- **Redis**: マッチングキュー / ルーム状態 / 再接続トークン（一時状態のみ、確定後のデータはPostgresへ）

## 外部連携

- Google / Apple IDプロバイダ（OAuthトークン検証）
- FCM（ターン通知、任意）

## この構成が前提にしている設計判断

- **権威判定はサーバー側のみ**。クライアントの計算はプレビュー表示用
- **再接続**: ルーム状態と直近の盤面はRedisに保持。切断→再接続時はルームIDとセッショントークンで状態を復元
- **観戦（将来拡張）**: マッチング/ルーム管理からの配信ストリームを読み取り専用の追加購読者に配ることで、対局ロジックを変更せず追加できる
- **4人麻雀拡張**: `mahjong_engine`は人数・牌構成をルール設定として受け取る想定（`RulesetDefinition.playerCount`、05参照）
- **リプレイ**: 着手イベント列をそのままPostgres/オブジェクトストレージに保存し、再生時は同じ`mahjong_engine`で再実行して盤面を復元
