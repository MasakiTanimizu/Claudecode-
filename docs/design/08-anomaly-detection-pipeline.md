# 追補: 異常検知ボタン・自動バグ判定パイプライン

STEP3（DB）・STEP4（通信）・STEP7（UI）・STEP9（オンライン設計、予定）を横断する機能。対局画面の「検知」ボタンから、Claude Codeによる自動バグ判定・修正パッチ作成・サンドボックス検証・人間レビュー・メンテナンスウィンドウでのデプロイまでの一連の流れを定義する。

## 検知ボタン（STEP7）

- 対局画面右上に常時表示する控えめなアイコンボタン
- 押すと軽量な確認シート（任意のひとことメモ欄＋送信ボタン）を表示。送信後は「ご報告ありがとうございます」の軽いトーストのみで、対局の進行は一切止めない
- クライアントはメモだけ送ればよい。`match_id`・現在の`seq_no`・アプリバージョン・プラットフォームはサーバー側でセッションから自動的に付与する

## DBスキーマ追加（STEP3）

### anomaly_reports

`id`(PK) / `match_id`(FK) / `reporter_user_id`(FK) / `reported_at_seq`(報告時点の`match_events.seq_no`) / `client_note`(text, nullable) / `app_version` / `platform` / `status`(new, analyzing, confirmed_bug, false_positive, needs_human_review, fix_drafted, fixed, wont_fix) / `ai_analysis`(jsonb, nullable) / `fix_pr_url`(text, nullable) / `created_at` / `resolved_at`

## 通信追加（STEP4）

`match.reportAnomaly(note?)` — 対局の進行状態には一切影響しない、完全に非同期の副作用のみのRPC。

## パイプライン

1. プレイヤーが「検知」を押す → `anomaly_reports`に1行追加（status=new）
2. 非同期ジョブが起動し、対局の`rule_config`・関連`match_events`・クライアントのメモをまとめてコンテキストを収集
3. Claude Codeが`mahjong_engine`のソースとルール仕様書（`docs/design`）を参照しながら、期待される挙動からの逸脱＝バグかどうかを判定
4. **バグでない** → `false_positive`として記録して終了
5. **バグと判定** → 修正パッチ＋回帰テストを作成（この時点ではまだPRを作らない）
6. **サンドボックスで検証**: 既存テスト全体・新規回帰テスト・報告された対局の再現replayを実行
   - 全て成功 → PRを作成し人間のレビューに提出（status=fix_drafted）
   - 1つでも失敗 → 自己修正を最大2回まで再試行。それでも失敗すれば`needs_human_review`として人間に判断を委ねる
7. **人間がレビュー・承認**（Claude Codeが作成したPRは自動マージしない）
8. 承認済みPRは毎朝9:00（JST）開始のメンテナンスウィンドウでのみ本番へデプロイ

## メンテナンスウィンドウ（毎朝9:00 JST〜）

- **8:00（1時間前）**: 承認済みPRがある日は、全プレイヤーへメンテナンス予告を通知（アプリ内バナー＋対局中はゲーム画面上部に常時表示）。新規マッチング受付もこの時点で停止
- **9:00**: 対局中であっても即座には打ち切らない。**進行中の局（1局）が自然に終了（和了・流局）するのを待ち、その局が終わった時点で対局を止める。** 次の局へは進ませず、その時点の持ち点を最終スコアとして`matches.end_reason = maintenance`で確定し、通常の対局終了と同じ計算式でウマ・素点ボーナス・祝儀を清算する
- 対局中でないプレイヤーがいなくなり次第（または一定の猶予時間の後）デプロイを開始し、ヘルスチェックを経て新規マッチング受付を再開

## 確定事項

- サンドボックス検証はPR作成の**前**に行い、全て成功したパッチのみPR化する
- Claude Codeが作成したPRは自動マージしない。人間がレビュー・承認してからマージする
- 9:00はJST
- 進行中の対局は1時間前通知の上、**局の途中では打ち切らない**。進行中の局が終わるまで待ってから対局を止める
